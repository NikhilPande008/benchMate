# Phase 2 report: diagnosis loop on the fake bench (Phase 2 + 2b, 3–4 Nov 2026)

## 2. Engine-level scenarios (no voice)

A scripted technician (`eval/scenarios/engine_run.py`) drives the 8 tools against the fake bench: it does what `next_step` says, reads through the camera (or aloud when asked), confirms read-backs, applies the fix and closes with the confirming reading the engine asks for. Run with `uv run python eval/scenarios/engine_run.py [--spoken] [--lang hi]`.

Camera readings:

| Scenario | True fault | Found | Outcome | Steps to root cause | Re-checks | Read-aloud asks | Degraded |
| --- | --- | --- | --- | ---: | ---: | ---: | --- |
| short_battery_line | vbat_cap_short | vbat_cap_short | fixed | 2 | 0 | 0 | – |
| no_current | open_vbat_path | open_vbat_path | fixed | 1 | 0 | 0 | – |
| not_charging | charge_path_part | charge_path_part | fixed | 2 | 0 | 0 | – |
| glare_low_confidence | vbat_cap_short | vbat_cap_short | fixed | 2 | 0 | 2 | – |
| conflicting_reading | power_key_line | power_key_line | fixed | 5 | 1 | 0 | – |
| camera_unavailable | open_vbat_path | open_vbat_path | fixed | 2 | 0 | 3 | camera_unavailable |
| vision_timeout | open_vbat_path | open_vbat_path | fixed | 2 | 0 | 3 | vision_timeout |

- **Robustness scenarios never gave a confident wrong answer.**
  - **Glare:** every unclear camera read (confidence 0.45–0.6) became a read-aloud request and never reached the ledger.
  - **Conflicting:** the slipped probe reading (vbat_conn read as short) raised a conflict on the next reading. The engine asked for one re-measure, the re-read superseded the slip, and only then did the fix come.
  - **Camera down:** degraded mode, every value read aloud, no power step approved. A variant where only a powered check could separate the faults ended "unresolved", not a guess (`test_repair.py`).
  - **Vision timeout:** the 4 s camera budget ran out, so the value was read aloud.
- **Spoken readings only** (`--spoken`, English and Hinglish): all 7 reach the scripted fault in 2 steps. A confirmed spoken reading counts at 0.85 instead of a camera read's 0.93–0.97, so no_current needs a second reading. With spoken readings the glitch and glare scenarios are no different from the others, because a spoken value is the true one.
- Every run closes as **fixed only after the reading that pointed at the fault came back healthy.** For example, chg_ic_in reads normal after the charging-path part is replaced. A boot watch alone no longer counts.

## 3. End-to-end spoken sessions (push-to-talk, mini, v3_local)

`eval/scenarios/voice_run.py`: Chrome with an injected microphone. A scripted technician reads the engine's state after every reply (`GET /dev/sessions/{id}`) and plays the next line as a synthetic clip (macOS `say`, voice Rishi; Hinglish in Latin script), holding the talk key for it. The model is the real `gpt-realtime-2.1-mini` with prompt v3_local and the local preamble clip.

**Fake bench.** Meter values are spoken (spoken readings only), except in glare_low_confidence and conflicting_reading, where the camera reads them. Supply reads and boot watches always come from the bench.

**No real clips:** `eval/intent_set/real/` has only its README, so there is no separate real-speech run.

The runs on 4 Nov found several bugs, each fixed with tests before the next run (§5). The last two complete batches, both after the stall fix:

**10 of 10 sessions reached the scripted root cause; 9 of 10 closed as fixed after a healthy check reading.** Across both batches:
- **No value spoken that wasn't in a tool result.** Each value the agent said was parsed and matched against earlier tool outputs, including read-backs in words.
- **No power instruction without a gate approval in the same turn.**
- **No stalled responses.**

Wrong turns:
- **not_charging 13:52:** the model filed "0.02 volt" (the charging-IC reading) under `vbus_port`, and the scripted "haan" confirmed it. That cost 2 extra steps. The model also said "Port damaged, replace…", reading the ranking aloud, although the engine had proposed no fix.
  - Fixed after this batch: a spoken value answers the step the engine is waiting for, and the read-back names the point. The 14:04 rerun took 2 steps.
- **glare 14:04:** after "haan", the model called `next_step` instead of confirming. `next_step` answered `confirm_readback` and the model asked again, 15 times. The diagnosis was already right (vbat_cap_short at 0.96); the session never closed.
  - Fixed after this batch: the user's own plain yes confirms the read-back. Unit-tested only (§7).
- **conflicting 14:04:** after the re-measure, the model said "Bad boot cable area — fix or remeasure the connection", reading the second-ranked fault aloud. The next step it gave was the engine's (power key).
- **short_battery_line:** the model sent a made-up point id (`vbat_cap`) to `get_reading` once, and once tried a boot watch while the heat check was waiting. The engine refused both (`unknown_point`, `not_this_step`) and the model recovered.

**Robustness behaved as required:**
- **Glare:** every unclear camera read became "Meter ki reading clear nahi aa rahi, value bolo"; no glare reading reached the ledger.
- **Conflicting:** the slipped vbat_conn reading raised a conflict and a re-measure ("Re-measure the VBAT connector area"). The re-read superseded the slip before any fix.

## 4. Language under v3 (synthetic voices)

Each agent reply is tagged by script and Hindi word list (`engine/telemetry/lang.py`); a "Hindi reply" is Devanagari or Hinglish.

| Where | Hinglish/Hindi lines → Hindi reply | English lines → English reply |
| --- | ---: | ---: |
| Spoken sessions, 13:52 + 14:04 (all replies) | **20 / 71 (28%)** | 28 / 30 (93%) |
| Latency set, v3_local (first 13 lines only, see §6) | 1 / 4 | 3 / 5 |
| Latency set, v2_local, same lines | 5 / 8 | 5 / 5 |
| 4 Nov, v2_local mini (plain lines) | 26 / 33 | 25 / 26 |

- **Hindi replies are the weak point of v3 on mini.** In Hinglish sessions the agent mostly answers in English, or English with a Hindi word, especially around tool results:
  - read-backs ("Zero point zero two volts, confirm karo" tags as English);
  - the gate's English sentence ("Connect the boot cable now.") instead of its Hindi one ("Ab boot cable lagao.").

  The exact-sentence rule held (every power line was one of the gate's two sentences), but the language choice did not.
- **Two English questions got Hinglish answers** on the latency set (p04, p05). `explain` returned only the session-language text (Hindi after the Hindi turns), and the model read it out. `explain` now returns both languages (unit-tested, not yet voice-tested).
- **Readings stay English values** in every prompt, as on 4 Nov ("Zero point four nine volts, diode mode"). The Hinglish example readings in v3 were not used.

## 5. Bugs the voice runs found (all fixed, with tests)

| Found | Effect | Fix |
| --- | --- | --- |
| agents-realtime 0.21.0 sends `conversation.item.retrieve` for every transcribed user item | The retrieved item (with the user's audio) holds up the WebRTC data channel for 2–6 s. The reply is audible but `response.created` and the next tool call arrive late, and the next turn queues behind them: 3–5 stalls per 26-turn session | The page drops that request (`voice.ts` `traceOutgoing`): **0 stalls** in every later session |
| "आगे" (ahead) matched "आग" (fire) as a substring | False safety stop on "aage batao" (transcribed in Devanagari) | Devanagari whole-word or stem matching; transcriber spellings added (`scope.py`) |
| The model said "boot cable connect karo" itself after a "power" step | A power instruction not from the gate (the engine still refused the watch) | `next_step` carries the gate's answer; `request_power_step` reads the supply itself |
| Invented or stale point ids; arguments to `next_step`; an approval spent on the wrong check; no phone model | Loops of `which_point` / `bad_args` | Fallback to the waiting step; arguments ignored; `not_this_step` + `use`; ask for the model; Devanagari aliases |
| "Nothing is getting hot" ≠ pack phrase "nothing hot" | 25 turns asking for a label | Phrases match with up to 2 words in between |
| Mini treated "capacitor garam" as a danger | 20 × "Disconnect everything now" | v3 Safety: a hot part during a heat check is the answer, not a danger |
| Value filed under the wrong point; read-back loop | Extra steps; a session that never closed | The waiting step wins, read-back names the point; the user's own "haan" confirms |
