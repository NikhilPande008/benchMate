# Latency report: 4 Nov 2026 (Phase 1b, fix and re-measure)

**In one paragraph.** End-of-turn detection was the biggest cost on 3 Nov, and push-to-talk removes most of it. With a simulated foot pedal, a person hears the reply 1.14–1.20 s after they stop talking (p50; p95 ≤ 1.32 s), against 1.67–1.92 s for semantic VAD. Push-to-talk also has no false cut-offs. Server VAD is predictable, but it cut 8–9 of the 10 lines that have a mid-sentence pause. A local pre-recorded preamble is heard about 1.0 s after the end of speech with push-to-talk. The second prompt iteration brings replies over 6 s down from 59% to 9–18%, and the cap now cuts only 0–2 of 45 replies. Connect time is now 3.9 s from page load to ready at p50 (3 Nov: 5.6–6.3 s, measured only from mic open). It is still short of 2 s, because the WebRTC setup with OpenAI alone takes about 3.8 s at the ~300 ms round trip from here. **No real recordings yet**, so every number below is from synthetic voices.

## Setup

- **Turn-driven harness, new this phase** (`apps/web/src/harness.ts`, `eval/latency_script/run_experiments.py`). The page plays each scripted clip into an injected audio stream only after the previous reply has finished (1.2 s of quiet). It records the exact wall-clock start and end of speech; the 3 Nov fake-WAV method had about ±300 ms of uncertainty. The stream carries a −60 dBFS noise floor. Without it, Chrome sends no packets during silence and the server's VAD never ends a turn.
- **Lines:** 45 synthetic lines, 30 plain and 15 tool, in English, Hinglish and Hindi (macOS voices Rishi and Lekha; `eval/latency_script/lines.json`). Nine lines (6 plain, 3 tool) have a scripted mid-sentence pause that measures 0.9–1.0 s.
- **Sessions:** every configuration ran all 45 lines in two sessions of 23 and 22 (below the 25-turn rotation point). Four configurations ran at a time in separate browsers against one engine. The dummy `get_reading` takes 1.5 s, and the model is `gpt-realtime-2.1-mini` unless stated.
- **Push-to-talk** is simulated: the key goes down 300 ms before the speech and up **200 ms after the true end** (an assumed human release lag). With a real pedal, the release lag is yours.
- **Real recordings:** `eval/intent_set/real/` is set up (see its README), but it has no clips yet, so there is no real-set table.
- **Network:** WebRTC round-trip time to OpenAI is 280–335 ms (p50 about 300 ms), measured every session.
- **Raw data:** `eval/latency_script/runs/x-20261104-b1/`, `x-20261104-b2/` and `connect-20261104/` (git-ignored). Tables come from `eval/latency_script/report_tables.py`.

Every cell is **p50 / p95 (n)** in milliseconds. With n = 15, p95 is close to the worst case.

## 1. Turn detection (mini)

| semantic_vad medium (v0, baseline) | 1011 / 2664 (45) | 1680 / 4134 (30) | 5/10 | 0/35 |
| semantic_vad medium (v1) | 1048 / 4703 (45) | 1884 / 5669 (30) | 4/10 | 0/35 |
| semantic_vad medium (v2_local) | 1123 / 4159 (45) | 1923 / 5193 (30) | 5/10 | 0/35 |
| semantic_vad high (v1) | 1053 / 2878 (44) | 1755 / 3898 (28) | 5/10 | 0/35 |
| server_vad 300 ms (v1) | 774 / 882 (44) | 1447 / 2150 (30) | 8/10 | 0/35 |
| server_vad 400 ms (v1) | 901 / 963 (43) | 1850 / 2381 (29) | 9/10 | 0/35 |

| **push-to-talk (v1)** | **513 / 546 (44)** | **1144 / 1289 (30)** | **0/10** | **0/35** |
| **push-to-talk (v2_local)** | **518 / 567 (44)** | **1195 / 1315 (28)** | **0/10** | **0/35** |

- For push-to-talk, the "server event" is `input_audio_buffer.committed`: the simulated 200 ms release lag plus about 300 ms for the commit to round-trip. Release → audible reply is therefore about 0.95 s.
- **Semantic VAD's p95 is its 4 s maximum wait.** It applied that wait to "रुको, एक मिनट" ("wait a minute"), which is correct, but also to some complete questions ("Which probe usually goes on ground in diode mode?": 4.8 s). Eagerness `high` did not help at p50.
- **Server VAD is steady (p95 within about 100 ms of p50) but cuts people off.** It ended the turn inside 8–9 of the 10 paused lines, and once that lost a reading request entirely ("प्रोब लगा दिया है, | अब मीटर पढ़ो" was answered as if it were only the first half). Lines without a pause had no false cut-offs in any mode.
- Real end → audible reply also includes the model's own response time. That varied from session to session (for example, server_vad 400's sessions were slower than 300's), so the end-of-turn column is the cleaner comparison of modes.

## 2. Preambles (tool lines)

| Configuration | Real end → preamble heard | Real end → value spoken | Model spoke before the result | Turn end → tool call |
| --- | --- | --- | ---: | --- |
| Model's own preamble (v0, semantic medium) | 1700 / 2301 (15) | 4215 / 4911 (12) | 15/15 | 781 / 1062 (15) |
| A: short model preamble "Checking." (v1, semantic medium) | 1899 / 3174 (14) | 4740 / 5664 (15) | 15/15 | 760 / 1121 (15) |
| B: local clip (v1_local, semantic medium) | 1489 / 2204 (15) | 3980 / 4737 (13) | 4/15 | 445 / 910 (15) |
| B: local clip (v2_local, semantic medium) | 1655 / 2625 (15) | 4260 / 5798 (11) | 2/15 | 551 / 851 (15) |
| A with push-to-talk (v1) | 1149 / 1387 (14) | 3544 / 3900 (14) | 14/14 | 570 / 920 (14) |
| **B with push-to-talk (v2_local)** | **989 / 1200 (15)** | **3415 / 3595 (12)** | 1/15 | 450 / 607 (15) |

- **B is heard sooner and the value comes sooner.**
  - **Heard sooner:** the clip starts on `response.output_item.added` and is audible 83 ms later (p95 91 ms, 69 clips) through the local WebRTC loopback, so it doesn't wait for the model to generate audio.
  - **Value sooner:** when the model speaks a preamble first, its tool call comes later. Under semantic medium, turn end → tool call was 445–551 ms with B and 760–781 ms with a model preamble. That gap varies from session to session across modes, so it is stated here for semantic medium only.
  - **No overlap:** the value reply waited for the clip on none of 69 lines, because the 0.54 s (English) or 0.82 s (Hindi) clip always ended before the 1.5 s tool finished.
- **The model doesn't always stay silent.** It spoke before the tool result on 4/15 lines with v1_local and 1–2/15 with v2_local on mini (0/15 on flagship). When that happens the clip is skipped or stopped, so the two never overlap.
- **The clip's language follows the previous turn** (the current turn's transcript isn't ready yet). In these sessions the language changes on almost every line, which is the worst case: the clip matched the line's language on 5–11 of 13–15 lines.
- **A mostly works as written:** 14 of 15 preambles began with "Checking" (10 exactly "Checking.", 3 "Checking now.", 1 "Checking the meter."), and one was "Theek hai, meter padho." It used "Checking." for Hindi lines too, not "Ek second."
- **The value takes 3.4–4.7 s at p50, against the 3.0 s target.** Taking the push-to-talk B line, it is made up of release lag (0.2 s), commit round trip (0.3 s), tool call (0.45 s), the 1.5 s stand-in tool, about 0.33 s for the next response to start, the model's time to first audio (0.4–0.7 s) and playout (0.15–0.2 s).
- **The tool result starts the next response at once.** The SDK sends `response.create` as soon as `execute()` returns; its sequencer holds it only while another response is in flight, and tool calls are dispatched after the preamble response is done. Result → `response.created` was 318–362 ms at p50 across all configurations, against a measured round trip of about 300 ms. That leaves about 30–60 ms of server time and no client-side wait.

## 3. Reply length

| Prompt (output cap) | Replies | Over 6 s of audio | Reply length p50 / p95 (s) | Cut by the cap |
| --- | ---: | ---: | --- | ---: |
| v0 (no cap), before | 44 | 26 (59%) | 8.3 / 22.1 | – |
| v1 (220 tokens), 7 configurations | 45–51 each | 35–49% | 4.6–6.0 / 7.7–8.1 | 8–13 each |
| v2_local, semantic medium | 45 | 8 (18%) | 3.5 / 6.9 | 2 |
| v2_local, push-to-talk | 45 | 4 (9%) | 3.2 / 6.5 | 1 |
| v2_local, flagship, semantic medium | 45 | 1 (2%) | 3.2 / 5.6 | 0 |
| v2_local, flagship, push-to-talk | 45 | 2 (4%) | 3.2 / 5.5 | 0 |

- **The cap is `max_output_tokens: 220`.** Measured: audio is generated at 20.0–20.6 tokens per second of reply, and `output_tokens = audio + text` (no hidden reasoning tokens at effort `low`). So 220 tokens is about 8 s of speech. Capped replies stopped at 7.4–8.3 s, mid-sentence.
- **v1** (two short sentences, about 15 words, three examples per language) halved the median, but the model still explained at length in Hinglish, and the cap became a hard limit on 1 reply in 4.
- **v2** (one sentence of at most 12 words, a second only if asked) is where the cap goes back to being a safety net.

## 4. Language (synthetic voices)

Replies tagged by script and Hindi word list (`engine/telemetry/lang.py`). "Hindi reply" means Devanagari or Hinglish.

| Prompt | Hindi plain lines → Hindi reply | Hinglish plain lines → Hindi reply | English plain lines → English reply |
| --- | ---: | ---: | ---: |
| v0 / v1 (mini, 8 configurations) | 6–8 of 7–8 | 7–9 of 9 | 4–11 of 13 |
| v2_local (mini) | 5/8, 7/7 | 7/9, 7/9 | 13/13, 12/13 |
| v2_local (flagship) | 6/8, 6/8 | 4/9, 3/9 | 13/13, 13/13 |

**Count you asked for:** with v2_local on mini (the recommended prompt), Hindi plain lines got a Hindi reply 12 of 15 times and Hinglish plain lines 14 of 18. With v1 it was 8 of 8 and 7 of 9 (semantic medium).

- **v1** answers English questions in Hinglish after a Hindi turn, and these sessions alternate languages, which is the worst case.
- **v2's "latest turn only" rule** fixed English but over-corrected: some Hindi and Hinglish questions now get English replies, most often on flagship.
- **Readings** were plain English values ("Zero point three five volts.") on every tool line in every prompt: 0 of 8–9 Hindi or Hinglish requests got a Hinglish sentence. Numbers in English are trade practice, but the Hinglish reading example is never used.
- **Transcripts** of Rishi's Latin-script Hinglish often come back in Devanagari, so the scripted line language is what counts here.
- **These are synthetic voices.** Real Hindi speech may well behave differently.

## 6. Connect time

Ten page loads each through the normal page, using Chrome's fake microphone so the real `getUserMedia` path is exercised. Stages are milliseconds after page load.

| Stage | Pool on (10) | Pool off (10) |
| --- | --- | --- |
| Inline script starts secret + mic | 5 / 8 | 4 / 9 |
| Client secret fetched | **10 / 12** | 846 / 1965 |
| Mic granted | 50 / 108 | 53 / 112 |
| SDP offer sent | 59 / 139 | 880 / 1976 |
| SDP answer back (POST /v1/realtime/calls) | 1703 / 2899 | 2403 / 7639 |
| Peer connection up (ICE + DTLS) | 2512 / 3761 | 3307 / 8465 |
| Data channel up, `session.created` | 3710 / 5005 | 4578 / 9740 |
| **Ready** (`session.updated`) | **3871 / 5136** | 4595 / 9762 |
| SDP POST duration | 1568 / 2837 | 1411 / 6405 |

- **What changed:**
  - The secret and mic start from an inline script before the 1.2 MB bundle loads.
  - The engine keeps one pre-minted secret per session config, refreshed before its 600 s expiry.
  - `preconnect` to api.openai.com.
  - The session opens on page load and stays open.
- **Why 2 s is out of reach on this connection.** From the SDP offer (59 ms) to ready takes 3.8 s, all of it between the browser and OpenAI at a ~300 ms round trip: SDP POST 1.6 s, then ICE + DTLS about 0.8 s, then the data channel about 1.2 s.
- **What could get under 2 s** (not done): a lower round trip (a closer region or a wired link), or keeping a warm session across page loads.
- **Before the pool fix,** pooled secrets lived 120 s and had always expired by the next page load. That is why the harness sessions in batch 1 all show a fresh mint (0.5–2.9 s). The fix gives pooled secrets 600 s and re-mints before expiry for any config used in the last 30 min. The second session of every batch-2 configuration was served from the pool.
- **Autoplay:** if Chrome blocks it on a fresh page load, the page shows a banner, and the first key press or click unlocks audio. A foot pedal's key press counts.

## Recommendation

1. **Turn mode:** make **push-to-talk on the foot pedal** the default at the bench.
   - It is the fastest mode, with no 4 s semantic waits and no false cut-offs, and it is not fooled by shop noise.
   - Keep **semantic_vad medium** as the hands-free mode, switchable live from the page; semantic high gave no gain.
   - Don't use server VAD unless your real recordings show natural pauses under 0.5 s: it cut 8–9 of 10 paused lines.
   - `CLAUDE.md` currently has semantic_vad as the decided default, so the code default is unchanged until you decide.
2. **Preamble:** use **B, the local clip, with the v2_local prompt.** It is heard about 1.0 s after speech with push-to-talk, and it doesn't delay the value. Code default prompt: `v2_local`.
3. **Model:** use **gpt-realtime-2.1-mini** for development and as the working default. It is faster and steadier. Flagship's shorter replies and better silence don't outweigh one 4.4 s-median session out of four. Revisit flagship for the demo after a real-voice quality check.
4. **Output cap:** keep `max_output_tokens: 220` (about 8 s) as the safety net. With v2 it cuts 0–2 replies in 45.

## Not shown here, or still open

- **Real voices.** All of this is macOS TTS. TTS pauses end with a falling, finished-sounding intonation, so false cut-off rates on real hesitant speech may differ in either direction.
- **The Hindi reply rate under v2** needs one more prompt iteration (keep v2's length rules, restore Hindi for Hindi turns), tested on real recordings.
- **Push-to-talk numbers assume a 200 ms release lag.**
- **Concurrency.** Configurations ran four at a time; all of them shared the same conditions, but absolute model times may be a little higher than in a single session.
- **Cost** was not recorded.
- **Echo with the local clip.** It was not tested acoustically (the harness has no speaker-to-mic path). The clip uses the WebRTC loopback path by design.
