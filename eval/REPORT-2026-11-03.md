Twenty scripted turns per model: 13 plain questions and 7 that should call `get_reading`. The lines are in English, Hinglish and Hindi, spoken by macOS voices (Rishi, Lekha) and played into Chrome's fake microphone through Playwright (headless Chrome, `--use-file-for-fake-audio-capture`). One session per model, run back to back on the dev laptop's home connection.

## What each number means
- **first_audio**: the client receives `input_audio_buffer.speech_stopped`, until it receives `output_audio_buffer.started`. This is the server's turn latency, and both timestamps are on the same browser clock.
- **audio_onset**: same start point, until audible sound on the remote WebRTC track (an `AnalyserNode` polled every 10 ms). Normally 135–280 ms after first_audio.
- **vad_lag**: the true end of the scripted line, until the client receives `speech_stopped`. This is the end-of-turn wait plus network. True end = mic open time + the line's offset in the WAV.
- **vad_tail** (cross-check): how much longer the server's VAD says the line lasted (`audio_end_ms − audio_start_ms`) than it really did. It uses only the server's audio clock, so it doesn't depend on the mic-open alignment. It slightly overstates, because it includes the VAD's prefix padding.
- **user_felt**: the true end of the line, until audible onset. This is the number a person feels.
- **value_audio** (tool turns): from `speech_stopped` to the first audio *after* the tool result reached the browser, i.e. when the value starts being spoken.

## Findings

1. **The model side is fast. The time is lost before the model starts.** After the server decides the turn has ended, first audio arrives in 0.44 s (mini) or 0.71 s (flagship) at p50, and under 0.9 s at p95 on both. That meets the 0.8 s target on its own.
2. **End-of-turn detection costs about 1 s.** The server's `speech_stopped` arrives 0.96 s (p50) after the line really ended, on both models. The server-clock cross-check agrees: it hears about 1.1 s more speech than there was. BUILD_GUIDE budgets 0.3–0.5 s for this. So what a person feels on a plain turn is **1.6–1.9 s at p50 and about 2.0 s at p95**, against a 0.8 s target. This is the biggest lever. Caveat: the speech is synthetic TTS with flat prosody and clean endings, and semantic VAD may behave differently on real speech.
3. **Preambles work and are on by default.** On 7 of 7 tool turns, both models spoke a preamble first (`response.done` phases `commentary,function_call`, then `final_answer`). The preamble reaches the ear 1.6–1.7 s after the line ends, mostly because of the VAD wait in finding 2.
4. **The spoken value is late, and the preamble is part of why.** Preamble playback lasted 1.5–2.8 s, *longer than the 1.5 s tool*. The value reply queues behind it: on two mini turns the value audio started within 50 ms of the preamble stopping. From the true end of the line to the value: 3.8 s (mini) or 4.8 s (flagship) at p50, against a 3.0 s target, and that is with a 1.5 s stand-in for a 1–2 s vision read. In order of size, the parts are: VAD wait (~1 s), tool (1.5 s), the rest of the preamble's playback, result → `response.created` (~0.32 s, consistent with one network round trip), and the model's time to first audio (flagship 0.6–0.9 s, mini 0–0.4 s).
5. **Replies run long.** On both models, 7 of 20 replies were still playing when the next line started 9–13 s later, so the server cut them (`output_audio_buffer.cleared`). That is longer than the prompt's "one or two short sentences". This run didn't save transcripts, so I can't say which sentences ran over. The script now records them.
6. **Tool choice was correct on every turn.** 20/20 on both models (7 tool calls, 13 plain answers). No realtime errors, no console errors, no turns lost.
7. **Language doesn't change latency.** Plain first_audio p50 by language (en / hi / hinglish): flagship 755 / 702 / 714, mini 440 / 425 / 447, with 3 to 7 turns each. Whether each reply was *in* the right language was not checked (no transcripts).
8. **Connecting takes 5.6–6.3 s** from mic open to `session.updated`. This run has no breakdown (the next run records client-secret and engine-ready times). "Connect early" (technique 13) matters.

## Model choice
On latency alone, **mini wins**: about 270 ms faster to first audio on plain and preamble turns at p50, and 1 s faster to the spoken value. Its plain-turn spread is wider (p95 874 vs 809). Both got tool choice right on every turn. The engine does the diagnosis reasoning, so mini's weaker reasoning matters less here than in a general assistant.

**Recommendation:** make mini the working default now. Choose the demo model after a quality pass with transcripts: reply language on Hindi turns, verbosity, and following the fixed power-step wording once Phase 2 adds it.

## What this run does not show
- Real voices, real Hindi and shop noise (Phase 4 recordings).
- Other networks: shop Wi-Fi, a phone hotspot.
- More than one session per model, and long sessions (latency drift after 20+ turns).
- Cost. Usage was not recorded.
- Echo behaviour. The fake mic hears no speaker output; AEC was on but had nothing to cancel.

## Worth testing next (needs a decision; not done here)
- Turn detection: `semantic_vad` eagerness `high`, `server_vad` with a short `silence_duration_ms`, and push-to-talk (a manual commit has no end-of-turn wait), all on *real* recordings.
- Shorter preambles. One fixed phrase of two or three words would cap preamble playback below the tool time.
- Tighter verbosity rules, checked against transcripts.
